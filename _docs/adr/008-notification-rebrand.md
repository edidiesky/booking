# ADR 008: Notification Email Template Rebrand, Visual Only

**Status**: Accepted
**Date**: 2026-07-11

## Context

Every existing notification handler (`booking-confirmed.handler.ts` and eight siblings in `packages/events-worker`) builds its own inline HTML string for the email body, with no shared visual shell. Font, color, and layout choices are duplicated and drift independently per handler, since nothing enforces a single source of truth for the visual design.

A reference `emailShell.ts` was reviewed showing a single `renderEmailLayout()` shell function every template composes against: Newsreader serif font loaded via Google Fonts, a fixed 560px centered card with 20px border radius, a heading, intro paragraph, optional info-row table for structured data (dates, amounts), a single primary CTA button, an optional secondary link, an optional closing note, and a wordmark-plus-tagline footer.

## Decision

Adopt the reference's visual shell exactly: same layout structure, same typography, same spacing. Rebrand only the following, nothing else:

- Font stack: Newsreader, matching the reference exactly.
- Color tokens: mapped to the booking platform's real CSS variables, not the reference's mislabeled blue "terracotta." `ink: #17191c`, `fog: #f7f7f8`, `mutedStone: #4c4c4c`, `lightSteel: #777b86`, `hintOfGrey: #a3a6af`, `canvas: #ffffff`, and the CTA/link accent color set to the platform's real terracotta, `#5d2a1a`.
- Wordmark: "Selleasi" becomes "Booking".
- Footer tagline: "Marketplace · Support · Help Center" becomes a booking-platform-appropriate equivalent.

## Explicitly out of scope, corrected from the prior draft of this ADR

No persisted notification audit trail. No `notification_log` table. No `notificationRepository`. No `IEmailProvider`/`ISmsProvider` interface abstraction. No `NotificationDispatcher`. No change to any handler's control flow, retry logic, idempotency key, or `BaseNotificationHandler` usage. Every handler continues calling `sendEmail(...)` exactly as it does today, calling into the existing `email.sender.ts`, the only change is the HTML string that function is passed, generated by the new shared shell instead of each handler's inline markup.

## Implementation shape

One new file, `packages/events-worker/src/templates/emailShell.ts`, exporting `renderEmailLayout(opts)` and the color/font token constants. Each of the nine existing template files (`booking-confirmed.template.ts` etc, wherever the inline HTML currently lives inside or alongside each handler) is edited to call this shell instead of constructing its own `<html>` string, passing the same data it already has, no new data requirements introduced.

## Consequences

**Positive**: visual consistency across every email guaranteed by construction, one shell, nine call sites, not nine independently maintained HTML strings. Small, low-risk diff, purely presentational.

**Negative**: none of real weight, this is a template swap with no behavioral change.

**Deferred, not decided against, simply not in scope here**: a persisted notification audit trail remains a real gap (no queryable record of whether a given email was actually sent), but is a separate future decision if and when it's actually wanted, not bundled into this visual rebrand.
